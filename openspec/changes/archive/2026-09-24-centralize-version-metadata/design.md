# 设计：版本来源与发布核对

## 背景

当前 `src/cli.ts` 将 `0.1.2` 写入 Commander，`package.json` 与 `package-lock.json` 另存版本；README 的本地包安装示例也包含固定文件名。CI 已运行类型检查、构建、测试和打包预览，但没有显式比较这些版本。详见 [提案](proposal.md) 和 [版本一致性规格](specs/version-consistency/spec.md)。

## 目标与非目标

**目标：** 构建与安装后的 CLI 使用包清单版本；本地和 CI 能发现清单、锁文件、CLI 输出不一致；发布前有明确的标签和 registry 核对步骤；当前使用文档不因下一次版本变化产生假“最新”信息。

**非目标：** 不为普通提交自动增加版本号或 Git 标签，不自动发布 npm，不修改已发布包、历史标签或带日期的历史验证事实。

## 决策

1. **以 `package.json` 为人工维护源。** `src/cli.ts` 从相对于自身位置的 `../package.json` 读取 `version`，使源码构建和 npm 全局安装读取各自包内的清单。相较继续在 CLI 写常量并用测试追赶，直接读取清单消除一处人工同步点；相较构建时生成版本文件，不增加生成步骤或构建工具依赖。若包清单损坏，CLI 应明确失败，而不是显示旧版本。
2. **把锁文件和可执行输出纳入检查。** 增加独立版本检查命令，比较 `package.json`、`package-lock.json` 顶层及根包版本，并在构建后执行 `dist/cli.js --version`。CI 在 build 之后运行该检查；现有 `npm ci`、类型检查和测试继续保留。检查命令只读，不改版本。测试覆盖一致和故意制造不一致的情形。
3. **发布标签采用单独的显式核对。** 普通 CI 不要求 HEAD 有新标签，因为 0.1.2 标签之后允许继续提交。维护者决定发布里程碑后，再核对预期名称 `v<package.json.version>`、目标提交和远端是否已有同名标签；版本变更使用 npm 的版本命令同步清单与锁文件，验证通过后才按维护者决定提交、打标签和推送。远端标签和 npm registry 分别作为实际发布状态核对，不能从本地文件推断。
4. **文档区分实时入口与历史快照。** README 本地安装示例使用打包命令返回的文件名，不写固定版本号；当前开发计划与 CLI 契约标题不再称某个版本为“当前源码”。CHANGELOG 和验证文档中已发生的版本、日期及结果保留为历史记录，并在表述中注明核对日期。需要知道 npm 当前最新版本时运行 `npm view`，不依赖旧快照。

## 风险与权衡

- [运行时包清单路径变化] → 使用相对 `dist/cli.js` 的包根路径，并在源码构建及隔离安装的打包产物中验证 `wk --version`。
- [CI 的 Git 标签不完整] → 普通 CI 只检查包内版本；标签核对在维护者发起的发布流程中执行，并读取远端标签状态。
- [文档历史数字被误判为需要更新] → 版本检查只覆盖当前包元数据和 CLI；历史条目保留原值，当前状态通过命令查询。

## 迁移计划

本变更不迁移用户数据。实施时先改 CLI 版本来源和检查，再调整文档及 CI；运行 `npm run check`、`npm run build`、版本检查、`npm test` 与 `npm pack --dry-run`。若出现兼容问题，可回退这次源码变更；不需要移动现有 Git 标签或重发已发布 npm 包。
