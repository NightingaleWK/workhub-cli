# Design

## Context

见 [proposal.md](proposal.md)。当前 `package.json` 仅将 `wk` 映射到 `dist/cli.js`，`package-lock.json` 同步记录该映射；Commander 程序名及多处运行时提示、当前文档使用 `wk`。本机全局 PATH 可解析到 `wk.ps1`，目前未发现 `workhub` 包装器。工作根目录使用 `.wk`，本机配置通过 `WK_CONFIG_PATH` 覆盖，两者与可执行命令名是不同的约定。

## Goals / Non-Goals

**Goals:**

- 让安装包只提供 `workhub` 入口，并在全局升级后清除该包留下的旧 `wk` 包装器。
- 让帮助、错误提示和当前使用说明统一以 `workhub` 引导用户。
- 在不触碰正式全局安装与用户工作空间的前提下验证 npm 打包和 Windows 命令包装器。

**Non-Goals:**

- 本次不重命名 npm 包、持久数据路径、环境变量或任务文件。
- 方案编写阶段不升级用户机器上的全局包；版本号、Git 标签和 npm 发布仍按独立发布流程决定。

## Decisions

### 1. 将 npm `bin` 中的命令改为 `workhub`

将 `bin.wk` 替换为 `bin.workhub`，仍指向 `dist/cli.js`，同步锁文件；Commander 的固定程序名改为 `workhub`。维护者已确认没有外部用户，不设置兼容别名，也不另建包装脚本。

### 2. 只替换命令调用语义中的 `wk`

逐处核对 `src`、内置模板、README、当前约定、发布步骤和 OpenSpec 项目上下文，将面向用户的命令示例与 `next` 提示改为 `workhub`。`.wk`、`WK_CONFIG_PATH`、`WK_PYTHON`、`wk-context.md`、`wk-handoff.md`、`WK:START` 等标识保留。历史开发计划、既往验证记录及已归档变更保留当时名称，避免改变历史证据。

### 3. 在隔离前缀中检验真实安装结果

先运行源码检查与构建，再打包并在临时 npm 前缀安装本地 tarball，检查只有 `workhub` 包装器，以及帮助、版本和只读命令。用临时工作根与 `WK_CONFIG_PATH` 检验旧配置可由新入口读取；必要的写入测试只写临时根。`npm pack` 内容须含模板和 LICENSE。随后检查正式全局 PATH 上的命令来源，再从已验证的本地包升级。

## Risks / Trade-offs

- [旧版全局安装的 `wk` 包装器残留] → 升级前记录其来源；升级后检查 `Get-Command wk -All`。若 npm 未清除旧包装器，仅针对确认归属本包的旧文件执行受控清理并复查，不触碰其他工具的同名命令。
- [PATH 上已有其他 `workhub` 命令] → 全局升级前检查命令来源；发生冲突时停止并由维护者决定，不覆盖无关工具。
- [机械替换损坏持久约定或历史记录] → 按语义审查每处命中，并用既有配置的隔离测试验证兼容性。
- [现有本机脚本仍调用 `wk`] → 当前确认没有外部用户；仓库内当前命令示例随实现更新，本机其他脚本如有命中则需改用 `workhub`。

## Migration Plan

1. 完成实现、隔离安装验证和 OpenSpec 同步归档；按仓库约定提交并推送源码。
2. 向维护者报告当前版本与标签，由维护者分别决定版本更新、标签及 npm 发布。
3. 实施阶段在隔离验证通过后，从经核对的本地打包文件全局安装；升级前记录 `wk` 来源，升级后核对 `Get-Command workhub,wk -All`、`workhub --version`，确认本包只留下 `workhub`。如旧 `wk` 包装器残留，核实归属后清理并复查。记录本地包来源；用户配置继续沿用，无数据迁移。这一步不等于 npm 公开发布。
4. 若新入口安装验证失败，保持现有 `wk` 使用；修复包后重新隔离验证。已升级的机器可按受控的包版本回退，并核对命令来源与配置读取。
