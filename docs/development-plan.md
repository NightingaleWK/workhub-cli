# workhub-cli 开发计划 V1.0

日期：2026-09-24
源码位置：`C:\Users\<用户名>\code\workhub-cli`
产品命令：`wk`
当前阶段：0.1.0 已实现并通过本地验证，详见 validation.md；下文保留原计划与验收边界

## 1. 项目目标

开发通过 npm 安装的 Windows 优先 CLI，实现个人 WorkHub 的交互初始化、工作创建、组成部分关联和登记索引维护。用户用菜单建立环境，AI 随后依据 Trellis 入口和目录映射开展分析、编码、验证和交接。

遵循已经确认的工作空间设计：

- 活动内容位于本地 SSD，根目录默认是当前 Windows 用户目录下的 WorkHub，允许输入其他路径。
- Trellis、业务知识库、代码分离；大小代码和一次性脚本都在 code。
- 日常 AI 本地项目固定 Trellis 为主，其他相关目录为附加目录，同一对话可以跨目录完成工作。
- work 和 archive 按创建年份组织；operations 按长期系统组织。
- 独立维护对象使用独立 Git 仓库，分类目录不建立父级仓库。
- FreeFileSync 负责备份到 OneDrive，wk 不重新实现备份系统。
- VS Code 工作区由用户手动创建，wk 仅维护预期路径并检查实际存在情况。

## 3. 第一版范围

### 必须完成

1. `wk install`：交互配置根目录、建立公共结构、重复执行检查补全。
2. `wk init`：中文名、英文代号、日期、多选组成部分、确认预览和执行。
3. work / trellis / code 独立选择；支持新建或关联已有 Trellis、代码仓库。
4. 生成必要 README、目录映射、Trellis 任务入口和初始交接。
5. 受控生成 AGENTS.md，不覆盖已有人工内容。
6. 新建独立对象的 Git 初始化，不自动提交或推送。
7. 一工作一登记文件，生成年度 Markdown 工作索引。
8. `wk list`、`wk show`、`wk check`。
9. 非交互参数与机器可读输出，供 AI 调用。
10. npm 本地打包、隔离安装和真实命令验证。

### 明确不进入第一版

- archive 自动搬移与 operations 智能提炼。
- 修改或迁移现有 OneDrive 工作资料。
- 自动创建 VS Code 工作区或自动设置 ChatGPT/Codex 项目。
- Git 远程创建、自动提交推送、自动部署。
- FreeFileSync 配置、调度或云端备份。
- GUI、数据库、后台服务和多人协作平台。
- 为所有历史项目自动批量升级模板。

这些边界不改变未来能力：第一版提供稳定登记和执行层，后续 AI 归档通过相同接口扩展。

## 4. 推荐技术方案

- TypeScript + Node.js，使用 npm 包发布形式，命令为 wk。
- Commander：命令与参数。
- @clack/prompts：文本输入、多选、确认和进度。
- Zod：用户输入、配置和登记数据验证。
- Vitest：临时目录中的行为测试。
- Node 内置文件系统、路径和进程 API；子进程使用参数数组，不拼接可执行 shell 文本。
- 编译优先采用简单的 tsc 流程；确有打包需求时再引入额外构建器。
- 运行时依赖随 npm 安装，模板作为包资源随包发布。

依赖的实际版本在实现开始时核实并通过 lockfile 固定。npm 包名及作用域在发布前确定，不假定 `wk` 或 `workhub-cli` 包名可用；包名与 bin 命令名相互独立。

## 5. 目录和配置

```text
<WorkHub>
├─ .wk
│  ├─ config.json
│  └─ runs
├─ trellis
├─ knowledge
│  ├─ work
│  ├─ archive
│  └─ operations
├─ code
└─ navigation
   ├─ README.md
   ├─ registry
   │  └─ works
   ├─ indexes
   │  ├─ 系统目录.md
   │  └─ 工作目录
   ├─ templates
   └─ workspaces
```

配置分为两层：

1. 本机配置建议位于 `%LOCALAPPDATA%\workhub-cli\config.json`，保存当前注册根目录。根目录恢复到新机器后重新注册，不依赖旧机器的绝对路径。
2. `<WorkHub>\.wk\config.json` 保存 schemaVersion、布局版本和模板版本等可迁移配置，不保存用户凭据。

根目录解析优先级：显式 `--root` > 本机登记根目录。未配置时提示执行 wk install；非交互模式返回明确错误，不静默创建默认根目录。

默认根目录用 `os.homedir()` 拼接 WorkHub，不硬编码用户名。第一版只维护一个当前注册根，允许显式切换但不自动迁移旧根。

每次操作在 `.wk/runs` 保存简要执行记录，不复制业务材料或记录密钥。导航目录独立 Git；`.wk` 和分类根不建立总仓库，其恢复由文件备份覆盖。

## 6. 命令契约

### 6.1 wk install

交互顺序：

1. 展示默认或已登记根目录，支持输入新地址。
2. 验证路径可用，展示将建立或复用的公共结构。
3. 核对导航仓库是否需要初始化。
4. 确认后执行；全部必要步骤完成后更新本机根目录指针。
5. 输出结果、根目录和下一步 wk init。

重复执行只补缺，不覆盖现有配置或人工文件。对已有非空未知根目录先检查，不直接将其当成新工作区管理。

`wk install` 初始化业务环境，不是安装 wk 程序本身。程序安装使用 npm install。

建议接口：`wk install --root <路径> --yes --json`。

### 6.2 wk init

```text
工作中文名：环保尾气上传程序逆向分析
英文代号：exhaust-analysis
工作日期：[今天]

空格多选，回车确认：
[x] work
[ ] trellis
[ ] code
```

交互策略：

- 默认勾选 work；至少选择一个组成部分。
- 日期按本机本地日期生成，不能用 UTC 截断造成日期偏移。
- 英文代号建议规则 `[a-z0-9]+(?:-[a-z0-9]+)*`；校验 Windows 保留名等路径限制。
- 中文名允许正常中文和空格，拒绝非法文件名、路径分隔符、尾部空格或点及越界片段。
- 日期使用 YYYY-MM-DD，严格验证真实日期。
- 工作编号为 YYYYMMDD-slug，业务目录为 knowledge/work/YYYY/YYYYMMDD-中文名。
- Trellis 和代码新建目录默认使用 slug，不带工作日期。
- 选中 trellis/code 时默认新建，支持主动关联已有目录；遇同名目录必须检查和明确复用，不覆盖。
- 首版关联对象限制在当前 WorkHub 对应类别目录内。历史外部项目先迁移或后续增加显式外部关联功能。
- 只选 code 或 trellis 仍建立工作登记；未启用 work 的任务不能声称有业务资料目录。
- 初始化末尾只做一次完整计划预览，确认后执行。

预览展示：工作编号、将创建或关联的目录、Git 操作、入口文件变化、工作区预留路径。

非交互示例（最终帮助文本与实现同步）：

```text
wk init --name "环保尾气上传程序逆向分析" --slug exhaust-analysis --date 2026-09-24 --components work,trellis,code --yes --json
```

建议另外提供 `--trellis-existing <相对路径>`、`--code-existing <相对路径>`。非交互选项相互冲突或参数不足时直接报错，不等待键盘。

### 6.3 wk list / show / check

| 命令 | 行为 |
|---|---|
| wk list | 从登记文件列出工作、日期、生命周期和组成部分 |
| wk show <id> | 展示实际路径、任务入口、仓库和工作区状态 |
| wk check [id] | 只读检查配置、路径、登记、入口、索引及仓库边界 |

check 区分错误和提示：缺失业务目录是错误，用户尚未创建预留工作区是正常待办提示。不得把工作区预留状态误报为初始化失败。

所有命令支持 `--help`；支持适用的 `--root`、`--json`。修改命令提供 `--dry-run`；`--yes` 只跳过已明确计划的交互确认，不跳过冲突和越界校验。

建议退出码：0 成功、1 执行或检查错误、2 参数错误、3 未解决冲突、130 用户取消。JSON 模式 stdout 只输出结构化结果，进度和诊断进入 stderr。

## 7. 登记与索引

每项工作一个 `navigation/registry/works/<id>.json`，至少包含：

```json
{
  "schemaVersion": 1,
  "id": "20260924-exhaust-analysis",
  "name": "环保尾气上传程序逆向分析",
  "slug": "exhaust-analysis",
  "createdDate": "2026-09-24",
  "lifecycle": "active",
  "components": {
    "work": { "path": "knowledge/work/2026/20260924-环保尾气上传程序逆向分析", "mode": "created" },
    "trellis": { "path": "trellis/exhaust-analysis", "mode": "created" },
    "code": [{ "path": "code/exhaust-analysis", "mode": "created" }]
  },
  "operations": [],
  "workspace": {
    "expectedPath": "navigation/workspaces/环保尾气上传程序逆向分析.code-workspace"
  }
}
```

Trellis 具体任务入口字段在适配验证后加入，不能预填未创建的任务地址。未选择的组件省略，不能生成虚假路径。

Markdown 索引完全由登记生成，使用稳定排序、明确标记自动生成。手写说明单独存放，不放在生成区。重新生成结果应可重复，不引入无意义时间戳差异。

登记仅保存关联和生命周期，不复制 Trellis 详细进度。模板渲染时转义 Markdown 表格特殊字符，保证中文名含竖线等字符时索引仍正常。

## 8. 工作区策略

默认预留 `navigation/workspaces/<中文名>.code-workspace`，不创建文件。

路径存在与否运行时检查，不在登记中缓存会过期的“已创建”状态。名称冲突时交互选择备用文件名，例如中文名-YYYYMMDD；非交互模式要求明确指定替代名称。

初始化输出用户应在 VS Code/AI 本地项目中选择的目录，并明确 Trellis 为主。应用 UI 配置属于人工步骤，工具不能把建议输出视为配置已完成。

## 9. Trellis 集成前置验证

必须先在临时目录验证本机 Trellis 的版本、帮助、初始化命令、任务创建接口，以及非交互能力。

检查它是否自动生成 Git、AGENTS.md、依赖或其他管理文件，避免与 wk 重复初始化。已有 Trellis 空间不重新初始化。

wk 与 Trellis 的责任：

- Trellis 提供正式管理结构和任务机制。
- wk 提供目录映射、模板化工作边界、索引与跨仓库关联。
- 任务记录使用实际 Trellis 机制，不建立与其并行的第二套任务状态。

生成或补充 AGENTS.md 时使用明确的 wk 管理区块；既有文件首次接入先预览差异，不盲目替换。受管区块有人工修改时检测冲突，保留原文。

Trellis 缺失或接口不支持时：选择该组件的计划在预检查阶段明确失败；不临时伪造一个空目录或假任务。第一版不自动安装/升级全局 Trellis。

## 10. 文件写入、Git 与失败恢复

执行分为四步：输入解析 → 全量预检查 → 计划确认 → 分步执行和核验。

必须满足：

- 所有受管路径验证位于目标类别目录内，考虑 Windows 大小写、符号链接和 junction 的实际路径，不仅字符串前缀判断。
- 先检测目标和 Git 根，禁止无意嵌套初始化。
- 只给新建独立对象初始化仓库；已有仓库保留分支、远程和未提交修改。
- 外部命令失败时保留错误证据，不报告整体成功。
- 写 JSON 和索引采用同目录临时文件加替换，减少半写文件。
- 同一根目录的写操作使用独占锁；异常残留锁提供明确恢复流程，不盲目删除。
- 执行日志记录每一步结果；部分失败可以安全重试。
- 对完全相同、已成功的 init 返回已存在及检查结果；参数不一致返回冲突。
- 部分初始化只有在日志和文件检查确认属于同一次操作时才能续作。
- 不以“回滚”为由递归删除已有资料；Git/Trellis 等外部操作不能假设完全可事务回滚。
- 完整成功后才写 active 登记；未完成状态保存在执行日志，不进入正常完成清单。
- 默认无 commit、push、远程创建和发布操作。

## 12. 分阶段实施与验收

### P0：环境与接口验证

产物：确认的 Node 支持范围、依赖版本、CLI 契约、Trellis 适配说明。

验收：在隔离目录完成一次真实 Trellis 初始化和任务创建，确认 AGENTS.md 与 Git 副作用。不能以模拟测试代替该项。

### P1：工程骨架和 wk install

产物：命令入口、配置 schema、根定位、公共结构创建、日志、基本预检查、帮助与版本。

验收：默认用户目录正确；自定义中文/空格路径正常；重复安装不覆盖；取消不修改；错误不会更新根指针。

### P2：wk init 核心与交互

产物：字段输入、多选、日期与名称校验、计划预览、业务模板、Git 和 Trellis 适配、关联已有组件。

验收：所有非空组件组合均符合契约；未选目录不创建；复用不重置；所有代码落在 code；Trellis 未完成不能显示成功。

### P3：登记、索引、查询与检查

产物：一工作一登记、年度索引、list/show/check、工作区预留及冲突处理。

验收：索引与登记一致；不产生重复工作；跨年创建和显示正确；工作区缺失显示待创建；相对路径迁移后能正确解析。

### P4：可靠性与 AI 非交互入口

产物：JSON 输出、明确退出码、dry-run、锁、原子文件写入、失败日志与续作。

验收：非 TTY 不挂起；失败可诊断可重试；已有文件不丢失；并发创建不互相覆盖；路径越界被拒绝。

### P5：打包与真实使用验收

产物：npm 安装包、安装使用文档、完整测试报告和已知限制。

验收：npm pack 后在隔离前缀安装并实际执行 wk；模板随包正确分发；运行不依赖源码工作目录；创建一个试点工作并通过入口与交接恢复检查。

发布到公共 npm 不属于默认验收动作，待用户明确授权。

## 13. 测试重点

测试关注真实风险，不为简单模板逐字建立大量镜像测试。

| 类别 | 必测情形 |
|---|---|
| 输入 | 中文、空格、空值、非法名、保留名、无效日期、闰日 |
| 日期 | 本地今天、跨年、手动指定历史日期 |
| 路径 | 相对路径、不同盘符、越界、已有目录、junction |
| 组件 | 七种非空组合、新建、复用、缺少 Trellis/Git |
| Git | 已有未提交修改、已有仓库、父仓库嵌套风险 |
| 登记 | 重复 ID、冲突参数、损坏 JSON、索引可重复生成 |
| 工作区 | 尚未创建、已有文件、同名冲突 |
| 失败 | 外部命令失败、写入失败、部分执行后重试 |
| 自动调用 | JSON 无菜单污染、非交互缺参报错、退出码 |
| 分发 | tgz 内容、隔离安装、模板路径和命令入口 |

文件操作测试使用临时目录和可注入本机配置路径，不修改真实 WorkHub、用户全局配置或原有项目。真实 Trellis 接口验证限定在隔离测试目录。

## 14. 后续版本

### 组成部分扩展

支持已有工作补建或关联 code/trellis，而不是重新 init 或人工编辑 JSON；具体命令在后续契约中确定。

### AI 驱动归档

预留 `wk archive <id> --check` 与 `--apply`。AI 完成业务验收检查和长期知识提炼，wk 执行路径检查、保留 Git 的目录移动、登记索引更新和已知引用修复。

归档年份按创建年份；代码和 operations 不随 work 移动。不能把结构检查通过等同于业务验收通过。

### operations 关联

后续支持建立长期知识对象、关联工作和证据索引。知识正文由 AI 按规范整理，CLI 不自动复制整份 work 形成重复资料库。

### 模板升级

按模板版本提供差异预览和受控应用，保留人工编辑，不在 npm 升级时自动重写业务文件。

## 15. 实施交付与授权边界
